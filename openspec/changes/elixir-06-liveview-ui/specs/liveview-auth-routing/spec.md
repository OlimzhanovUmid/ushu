# liveview-auth-routing

Authentication and routing for the LiveView UI: `phx.gen.auth` adapted to
username+password, role-based `on_mount` guards, and `live_session` blocks in
the router. Roles come from the `users` schema defined in `elixir-03-ecto-schema`
(`role` enum `[:admin, :main_judge, :judge]`, `category` enum `[:a, :b, :c]`
set only for `role: :judge`, `active` boolean).

## ADDED Requirements

### Requirement: Login is username plus password with no email flows

The system SHALL authenticate users by `username` and password using the
session-based flow generated by `mix phx.gen.auth`, adapted so that no email
field, email confirmation, magic link, or password-reset-by-email flow exists.
Login MUST reject inactive users (`active: false`) with the same generic error
as a wrong password.

#### Scenario: Successful username login

- **WHEN** an active user submits a correct username and password on the login page
- **THEN** a session is created and the user is redirected to the screen for their role (judge console, secretary console, or scores review)

#### Scenario: Inactive user cannot log in

- **WHEN** a user whose `active` flag is false submits correct credentials
- **THEN** login fails with the generic invalid-credentials message and no session is created

#### Scenario: No email surface exists

- **WHEN** any client requests an email-confirmation, magic-link, or password-reset route
- **THEN** the route does not exist (404) — these flows were removed, not just hidden

### Requirement: Role guards run in on_mount for every authenticated LiveView

Every authenticated LiveView SHALL be protected by an `on_mount` hook (e.g.
`{UshuWeb.UserAuth, {:ensure_role, roles}}`) attached via its `live_session`.
The guard MUST run on both the disconnected and connected mounts, MUST halt
with a redirect to the login page when no user is authenticated, and MUST halt
with a redirect and a flash error when the user's role is not in the allowed
set. Role checks SHALL never rely on the client (no hidden UI as the only
barrier).

#### Scenario: Anonymous user opens a judge console

- **WHEN** an unauthenticated browser navigates to the judge route
- **THEN** the mount halts and redirects to the login page; no scoring data is sent to the client

#### Scenario: Judge opens the secretary console

- **WHEN** a logged-in user with role `:judge` navigates to the secretary route
- **THEN** the mount halts, the user is redirected away with an error flash, and no secretary action is possible

#### Scenario: Direct websocket connect bypassing the dead render

- **WHEN** a client attempts to join the LiveView websocket for a protected view without a valid session
- **THEN** the connected mount's `on_mount` guard halts the join

### Requirement: Router organizes screens into role-scoped live_sessions

The router SHALL define `live_session` blocks so that navigation between views
of the same role keeps one websocket, and crossing a role boundary forces a
full remount: `:judge` (judge consoles), `:main_judge` (score review; also
accessible to `:admin`), `:admin` (secretary console, print protocol), and a
public `:monitor` session for the projector. All authenticated sessions SHALL
share the app root layout showing the current user's name, role, and a logout
control.

#### Scenario: Session boundary forces remount

- **WHEN** an admin navigates from the secretary console to a route in a different live_session
- **THEN** the current LiveView socket is torn down and a fresh mount (with its own on_mount guards) occurs

#### Scenario: Monitor needs no credentials

- **WHEN** the projector machine opens the monitor route with no session cookie
- **THEN** the monitor renders (it displays only public competition data)

### Requirement: One judge entry route dispatches by category

The system SHALL expose a single judge entry route (`/judge`) whose mount
selects the console for the logged-in judge's `category`: `:a` renders the A
console, `:b` the B console, `:c` the C console. A judge whose category does
not match a console (nil) SHALL see an error screen instructing to contact the
admin, never a crash.

#### Scenario: B judge logs in

- **WHEN** a user with role `:judge` and category `:b` opens `/judge`
- **THEN** the B console (numpad scoring) is mounted

#### Scenario: Judge with missing category

- **WHEN** a user with role `:judge` and `category: nil` opens `/judge`
- **THEN** a friendly configuration-error message is rendered and nothing crashes

### Requirement: Admin can manage users from the UI

The admin SHALL have a users screen to create judges (username, password,
role, category), deactivate/reactivate them, and reset passwords — via the
`Ushu.Accounts.create_user/1`, `deactivate_user/1` and `reset_password/2`
context functions provided by `elixir-04-contexts`. Deleting a
user with recorded scores is not offered — deactivation is the retirement path
(FK protection comes from `elixir-03-ecto-schema`).

#### Scenario: Admin resets a judge password

- **WHEN** the admin sets a new password for a judge account
- **THEN** the judge can log in with the new password and existing sessions of that user are invalidated

#### Scenario: Deactivation instead of deletion

- **WHEN** the admin deactivates a judge
- **THEN** the judge can no longer log in, and per `elixir-04-contexts` registration stops creating score cards for them
