# 05 — Realtime: процессы, GenServer, PubSub и Presence

**Слой 5 из 7** (`elixir-05-realtime`). Зависит от `elixir-01-foundation`
(приложение и PubSub уже запущены) и стыкуется с `elixir-04-contexts`
(кто *отправляет* события) и `elixir-06-liveview-ui` (кто их *принимает*).

## Какой это слой и зачем

Всё «реалтаймовое» в Django-версии ushu — это обходные пути: монитор писал
готовый HTML в файлы `showme*.html` рядом с шаблонами, проектор тянул их через
SSE с самодельным retry, а экраны судей опрашивали сервер по таймеру. Django —
это по сути «запрос пришёл → ответ ушёл → всё забыли»; между запросами негде
держать живое состояние и некому «толкнуть» браузер.

В Elixir/Phoenix всё наоборот: сервер — это тысячи маленьких живых процессов,
которые умеют слать друг другу сообщения. Этот слой определяет три вещи:

1. **Каталог событий PubSub** — какие именно сообщения летают по системе, кто
   их шлёт и кто слушает (контракт между слоями 04 и 06).
2. **`Ushu.Competition.MonitorBoard`** — маленький процесс (GenServer), который
   держит в памяти «что сейчас показывает проектор».
3. **`UshuWeb.Presence`** — секретарь видит, какие судьи сейчас онлайн (новая
   возможность, которой в Django-версии не было).

## Ключевые концепции Elixir/Phoenix в этом слое

### 1. Процессы и почтовые ящики (mailboxes)

Фундамент всего. В BEAM (виртуальной машине Erlang) **процесс** — это не поток
ОС и не корутина Kotlin, а сверхлёгкая изолированная единица исполнения
(~2–3 КБ памяти на старте). Их спокойно бывают сотни тысяч. У каждого процесса:

- **свой изолированный heap** — никакой разделяемой памяти, нечего лочить;
- **почтовый ящик (mailbox)** — очередь входящих сообщений;
- **pid** — адрес, по которому ему можно послать сообщение.

Три примитива: `spawn` (создать процесс), `send` (положить сообщение в ящик),
`receive` (достать из ящика с pattern matching):

```elixir
pid = spawn(fn ->
  receive do
    {:hello, from} -> send(from, {:reply, "привет!"})
  end
end)

send(pid, {:hello, self()})

receive do
  {:reply, text} -> IO.puts(text)   # => привет!
end
```

Параллель с Kotlin: это очень похоже на **actor + Channel** из корутин
(`actor { for (msg in channel) ... }`), только акторы здесь — не библиотека,
а сама модель исполнения рантайма. Ключевые отличия от корутин:

- **Изоляция**: у корутин общая куча — можно случайно шарить mutable-состояние.
  У процессов BEAM общей памяти нет вообще; сообщение при отправке копируется.
- **Вытесняющая многозадачность**: корутина, ушедшая в вечный цикл без
  suspension point, вешает поток. Процесс BEAM планировщик прервёт
  принудительно (по бюджету редукций) — один сумасшедший процесс не положит
  систему.
- **Смерть изолирована**: необработанное исключение убивает *один процесс*,
  а не JVM.

В нашем приложении процессами являются: каждое websocket-соединение, каждый
LiveView каждого судьи, `MonitorBoard`, сам `Repo`-пул… Когда судья A нажимает
«отправить оценку», работает *его* процесс; проектор в этот момент — *другой*
процесс, который просто ждёт сообщений в своём ящике.

### 2. GenServer: процесс с состоянием и API

Писать голые `spawn`/`receive`-циклы вручную — как писать сырые сокеты вместо
Spring MVC. **GenServer** («generic server») — это стандартный каркас OTP для
процесса, который: держит состояние, отвечает на синхронные вызовы (`call`),
принимает асинхронные команды (`cast`) и произвольные сообщения (`info`).

Грубая аналогия из Spring: singleton-бин с состоянием, у которого **все методы
как будто synchronized** — но без блокировок: сообщения обрабатываются строго
по одному, из очереди. Сериализация доступа бесплатно и без deadlock'ов.

Вот наш `MonitorBoard` целиком — это одновременно и полный учебный пример
GenServer:

```elixir
defmodule Ushu.Competition.MonitorState do
  @type mode :: :idle | :performing | :scores | :standings
  @type t :: %__MODULE__{mode: mode(), data: map() | nil, updated_at: DateTime.t() | nil}

  defstruct mode: :idle, data: nil, updated_at: nil
end

defmodule Ushu.Competition.MonitorBoard do
  use GenServer

  alias Ushu.Competition.{Events, MonitorState}

  ## --- Клиентский API (выполняется в процессе ВЫЗЫВАЮЩЕГО) ---

  def start_link(_opts) do
    GenServer.start_link(__MODULE__, :ok, name: __MODULE__)
  end

  def publish_performing(data), do: GenServer.cast(__MODULE__, {:publish, :performing, data})
  def publish_scores(data),     do: GenServer.cast(__MODULE__, {:publish, :scores, data})
  def publish_standings(data),  do: GenServer.cast(__MODULE__, {:publish, :standings, data})
  def clear,                    do: GenServer.cast(__MODULE__, :clear)

  @spec current() :: MonitorState.t()
  def current, do: GenServer.call(__MODULE__, :current)

  ## --- Callbacks (выполняются В ПРОЦЕССЕ GenServer'а) ---

  @impl true
  def init(:ok) do
    state = %MonitorState{mode: :idle}
    # после рестарта (краша) все проекторы должны сойтись с доской:
    Events.broadcast_monitor_updated(state)
    {:ok, state}
  end

  @impl true
  def handle_call(:current, _from, state) do
    {:reply, state, state}
  end

  @impl true
  def handle_cast({:publish, mode, data}, _old_state) do
    state = %MonitorState{mode: mode, data: data, updated_at: DateTime.utc_now()}
    Events.broadcast_monitor_updated(state)
    {:noreply, state}
  end

  def handle_cast(:clear, _old_state) do
    state = %MonitorState{mode: :idle, updated_at: DateTime.utc_now()}
    Events.broadcast_monitor_updated(state)
    {:noreply, state}
  end
end
```

Что здесь важно понять:

- **`init/1`** — вызывается один раз при старте процесса, возвращает начальное
  состояние. Аналог `@PostConstruct`.
- **`handle_call/3`** — синхронный запрос-ответ: вызывающий процесс *блокируется*
  (по умолчанию до 5 секунд), пока не придёт `{:reply, ответ, новое_состояние}`.
  Используем для `current/0` — проектору при монтировании нужен ответ сейчас.
- **`handle_cast/2`** — «выстрелил и забыл»: вызывающий не ждёт. Используем для
  `publish_*` — секретарю не нужен ответ, а подтверждение придёт всем через
  PubSub-событие.
- **`handle_info/2`** (в этом модуле не нужен) — приём «сырых» сообщений,
  посланных обычным `send`. Именно через него LiveView получает PubSub-события
  (см. ниже).
- **Состояние — просто значение**, которое каждый callback принимает и
  возвращает. Никаких полей, никакого `var` — «мутация» это возврат нового
  структа. Как `copy()` у data class в Kotlin, только это единственный способ.
- **`name: __MODULE__`** — регистрация процесса под именем модуля, чтобы вся
  система обращалась к нему без знания pid: `MonitorBoard.current()`.
  Аналог singleton-бина, найденного по типу.

Разделение «клиентский API / callbacks» — важная идиома: функции `publish_*`
выполняются в процессе вызывающего (LiveView секретаря) и лишь кладут сообщение
в ящик; callbacks выполняются в самом процессе доски, строго последовательно.
Гонок между двумя одновременными publish быть не может *по построению*.

### 3. Деревья супервизии и «let it crash»

В Spring, если бин бросил исключение — вы ловите его где-то выше и надеетесь,
что состояние бина не осталось битым. В OTP философия другая: **не защищайся
от каждой ошибки — позволь процессу умереть, и пусть супервизор поднимет
свежий**. Это «let it crash».

**Supervisor** — специальный процесс, который следит за детьми и перезапускает
их по стратегии. Наше дерево (в `Ushu.Application`, слой 01 + этот):

```elixir
def start(_type, _args) do
  children = [
    UshuWeb.Telemetry,
    Ushu.Repo,
    {Phoenix.PubSub, name: Ushu.PubSub},
    UshuWeb.Presence,                 # ← этот слой
    Ushu.Competition.MonitorBoard,    # ← этот слой
    UshuWeb.Endpoint
  ]

  opts = [strategy: :one_for_one, name: Ushu.Supervisor]
  Supervisor.start_link(children, opts)
end
```

- **`:one_for_one`** — умер ребёнок → перезапускается только он. Есть ещё
  `:one_for_all` (умер один → рестарт всех) и `:rest_for_one` (рестарт умершего
  и всех, кто стартовал после него) — нам не нужны: доска не зависит от
  Presence и наоборот.
- **`:permanent`** (рестарт-стратегия ребёнка по умолчанию) — перезапускать
  всегда, чем бы ни кончился. Порядок в списке важен: PubSub должен стартовать
  раньше доски, потому что `init/1` доски уже делает broadcast.
- Супервизор считает интенсивность рестартов (по умолчанию 3 за 5 секунд);
  если ребёнок падает в цикле — падает сам супервизор, и проблема эскалируется
  вверх по дереву. Ошибки не замалчиваются, а всплывают структурированно.

Что это значит для `MonitorBoard` конкретно:

1. Доска упала (скажем, кто-то передал битые данные и pattern match не сошёлся).
2. Умер **только** процесс доски. LiveView проекторов живы, их подписки живы —
   подписки хранятся в PubSub, а не в доске.
3. Супервизор мгновенно стартует новую доску. `init/1` ставит `:idle` и
   рассылает `{:monitor_updated, idle}` — все проекторы честно показывают
   заставку (а не устаревшие баллы, о которых новая доска ничего не знает).
4. Секретарь замечает и жмёт «показать» ещё раз. Цена восстановления — один клик.

Заметьте: мы **не пишем ни одного `try/rescue`** внутри доски. Код описывает
только правильный путь; неправильный путь обрабатывает супервизор. Это и есть
причина легендарной живучести Erlang-систем.

### 4. Phoenix.PubSub: как на самом деле работает «подписка»

`Phoenix.PubSub` — это не брокер вроде RabbitMQ и не Redis. На одном узле это
просто **реестр в памяти**: «тема (строка) → список pid'ов подписчиков».
Broadcast — это цикл `send(pid, message)` по списку. Всё, никакой магии,
никакой сериализации, микросекундные задержки.

```elixir
# подписаться (вызывается в процессе, который хочет получать):
Phoenix.PubSub.subscribe(Ushu.PubSub, "competition")

# опубликовать (из любого процесса):
Phoenix.PubSub.broadcast(Ushu.PubSub, "competition", {:score_saved, 42})
```

Сообщение падает подписчику в обычный почтовый ящик, и LiveView получает его
в `handle_info/2`:

```elixir
defmodule UshuWeb.ScoresLive do
  use UshuWeb, :live_view
  alias Ushu.Competition.Events

  @impl true
  def mount(_params, _session, socket) do
    if connected?(socket), do: Events.subscribe_competition()
    {:ok, load_scores(socket)}            # ВСЁ состояние — из БД, при каждом mount
  end

  @impl true
  def handle_info({:score_saved, _score_id}, socket) do
    {:noreply, load_scores(socket)}       # событие — лишь сигнал «перечитай»
  end
end
```

Параллели: `ApplicationEventPublisher` в Spring — похожая идея (издатель не
знает слушателей), но события Spring синхронны и живут внутри одного вызова;
PubSub асинхронен и связывает *независимые процессы*. А
`SimpMessagingTemplate`/STOMP — это доставка в браузер; у нас эту часть берёт
на себя LiveView: событие приходит в серверный процесс вью, тот перечитывает
данные и Phoenix сам шлёт браузеру минимальный diff DOM.

Наш каталог событий зафиксирован в одном модуле, чтобы строки-темы не
расползались по коду:

```elixir
defmodule Ushu.Competition.Events do
  @competition "competition"
  @monitor "monitor"

  def subscribe_competition, do: Phoenix.PubSub.subscribe(Ushu.PubSub, @competition)
  def subscribe_monitor,     do: Phoenix.PubSub.subscribe(Ushu.PubSub, @monitor)

  def broadcast_performance_started(id),   do: bc(@competition, {:performance_started, id})
  def broadcast_score_saved(id),           do: bc(@competition, {:score_saved, id})
  def broadcast_score_reopened(id),        do: bc(@competition, {:score_reopened, id})
  def broadcast_performance_finalized(id), do: bc(@competition, {:performance_finalized, id})
  def broadcast_monitor_updated(state),    do: bc(@monitor, {:monitor_updated, state})

  defp bc(topic, msg), do: Phoenix.PubSub.broadcast(Ushu.PubSub, topic, msg)
end
```

Кто что шлёт и слушает:

| Событие | Производитель | Потребители |
|---|---|---|
| `{:performance_started, id}` | `Ushu.Competition` (активация, слой 04) | все экраны судей, секретарь, ScoresLive |
| `{:score_saved, id}` | `Ushu.Competition` (submit судьи, слой 04) | ScoresLive (гл. судья), секретарь |
| `{:score_reopened, id}` | `Ushu.Competition` (reopen, слой 04) | экран конкретного судьи, ScoresLive |
| `{:performance_finalized, id}` | `Ushu.Competition` (финализация, слой 04) | все экраны судей, секретарь |
| `{:monitor_updated, %MonitorState{}}` | `MonitorBoard` (этот слой) | MonitorLive (проектор) |

Два правила контракта:

- **События «тонкие»** — несут только id. Получатель перечитывает БД сам
  (исключение — `%MonitorState{}`: там снапшот и есть готовые данные).
- **Broadcast только после коммита.** Событие уходит после того, как
  `Repo.transaction` вернул `{:ok, _}`. Иначе подписчик может перечитать БД и
  увидеть состояние *до* отката — фантомное событие.

### 5. Presence: кто онлайн (и причём тут CRDT)

`Phoenix.Presence` — надстройка над PubSub, отвечающая на вопрос «какие
процессы сейчас числятся на теме, с какими метаданными». Судья открыл экран —
его LiveView-процесс регистрируется:

```elixir
# в on_mount-хуке (сам хук — слой 06; контракт — этот слой):
UshuWeb.Presence.track(self(), "presence:judges", to_string(user.id), %{
  username: user.username,
  role: user.role,          # :judge | :main_judge
  category: user.category,  # :a | :b | :c | nil
  online_at: DateTime.utc_now()
})
```

Главная прелесть — **уход отслеживается автоматически**: Presence мониторит
процесс, и когда тот умирает (закрыл вкладку, уснул ноутбук, выдернули кабель —
websocket-heartbeat заметит мёртвого пира), запись исчезает и подписчики темы
получают `"presence_diff"`. Никаких «logout»-хендлеров и таймаут-крон-джобов,
как пришлось бы городить в Django.

Ключ записи — id пользователя, поэтому два таба одного судьи — это **один ключ
с двумя метами**: судья «онлайн», пока жив хотя бы один процесс. Закрыл один
таб из двух — в панели секретаря ничего не мигнуло.

Почему в описании Presence всегда звучит слово **CRDT** (Conflict-free
Replicated Data Type)? Presence спроектирован для кластера: каждый узел ведёт
свою реплику списка присутствующих, реплики обмениваются дельтами и **сходятся
к одному состоянию без центрального арбитра** — специальная структура данных
(ORSWOT — observed-remove set) гарантирует, что конкурентные join/leave на
разных узлах не конфликтуют. У нас узел один, так что CRDT-механика работает
«вхолостую», но знать её стоит: это то, что позволит завтра поставить второй
сервер без единой строчки изменений в коде Presence.

Важное решение: **Presence — только индикатор, никогда не источник истины.**
Валидность оценки, состав панели, полнота карточек — это факты БД (слой 04).
Presence eventually consistent (уход виден с задержкой heartbeat-таймаута,
~30–60 с), и блокировать на нём доменные операции значило бы добавить им
случайные отказы. Секретарь видит панель «кто онлайн» и может *решить*
подождать судью — но система не запрещает ей действовать.

### 6. Почему БД — источник истины, а GenServer держит только эфемерное

Самый важный архитектурный пункт слоя. У нас есть соблазн: раз GenServer так
удобно держит состояние — почему бы не держать в нём текущее выступление,
оценки, а БД обновлять «потом»? Так делают, например, игровые серверы.

Мы делаем строго наоборот, и вот почему:

1. **Данные соревнования драгоценны и редки.** Десяток записей в минуту — для
   SQLite это ничто, а вот потерять оценку из-за краша процесса на живом
   турнире — катастрофа. Всё, что жалко терять, коммитится в БД немедленно.
2. **Let it crash работает только с дешёвым состоянием.** Супервизор может
   безболезненно перезапустить `MonitorBoard` именно потому, что его состояние
   ничего не стоит: это *проекция для дисплея*, восстанавливаемая одним кликом
   секретаря. Если бы там жили оценки, каждый краш был бы потерей данных, и
   пришлось бы городить персистентность состояния — теряя всю простоту.
3. **Однозначность чтений.** Протокол, итоги, пересмотр оценок — всё читает
   одну и ту же БД. Нет вопроса «а доска и БД сейчас согласованы?» — доска
   вообще не хранит фактов, только «что показать на проекторе».

Итого правило: **GenServer — для эфемерного, БД — для фактов.** `MonitorBoard`
хранит ровно одно эфемерное значение: `%MonitorState{mode, data}`.

**Когда выбрали бы иначе.** Держать авторитетное состояние в процессе (и
сбрасывать в БД лениво/периодически) оправдано, когда: (а) состояние меняется
сотни раз в секунду и БД не успевает (позиции игроков, курсоры совместного
редактора, телеметрия); (б) состояние легко восстановимо из внешнего источника
и является кэшем; (в) допустима потеря последних N секунд. Наш кейс —
противоположность по всем трём пунктам. Если бы ushu стал, скажем,
многоковровым с бегущим таймером выступления на 10 табло — таймер (эфемерный,
тикающий) жил бы в процессах, а результаты всё равно в БД.

### 7. Переподключение: почему пропущенные события не страшны

LiveView-клиент (JS в браузере) сам переподключается с экспоненциальным
backoff — бесплатно, без нашего кода (в Django пришлось отдельно чинить
100-миллисекундный retry-шторм SSE). При переподключении сервер заново
выполняет `mount/3`.

Отсюда наше правило из примера выше: **`mount` собирает полное состояние из БД
и `MonitorBoard.current/0`, события — лишь сигналы «перечитай»**. Тогда
пропущенные за время обрыва события не значат ничего: свежий mount не зависит
от истории событий. Не нужны sequence numbers, replay, журнал доставки —
т.е. 90% сложности «надёжного» месседжинга мы вычёркиваем одним паттерном.

## Решения и почему

Кратко по решениям из `design.md` (D1–D9), человеческим языком:

- **Тонкие события с id (D1).** Альтернатива — слать в событии сами данные
  («жирные» события). Отвергли: события могут обгонять друг друга, и подписчик
  отрисует устаревший payload; а перечитать SQLite стоит микросекунды.
  Исключение — `%MonitorState{}`: он уже готовая картинка для дисплея.
- **Один модуль `Events` (D2).** Иначе строки `"competition"` расползутся по
  контекстам и вью, и контракт слоёв 04/05/06 не будет жить нигде. Аналог —
  выделенный класс констант вместо магических строк.
- **Одна глобальная тема, не по-табловая (D3).** Частичный уникальный индекс
  гарантирует: выступает максимум один участник; подписчиков ~10. Темы вида
  `"competition:tablo:#{id}"` — правильный паттерн для «много арен», нам не нужен.
- **GenServer, а не Agent/ETS/строка в БД (D4).** Нужны: сериализация записей +
  побочный эффект (broadcast) на каждую запись + синхронный `current/0` —
  это определение GenServer. Agent не даёт места для side effect'а, ETS — это
  оптимизация чтений, которых у нас три в минуту, строка в БД — персистентность
  того, что нарочно эфемерно.
- **Краш → `:idle` + broadcast сброса (D5).** Альтернатива — сохранять снапшот
  (ETS-heir, диск) и восстанавливать. Отвергли: механика ради значения ценой в
  один клик, плюс восстановленный снапшот может втихую разойтись с БД. Проектор
  после краша показывает заставку — *никогда не неверные данные*.
- **Broadcast после коммита (D6).** Внутри `Ecto.Multi` слать нельзя: откат БД
  не отзовёт уже отправленное сообщение.
- **Presence по ключу user id (D7) и только как индикатор (D8).** См. выше.
- **Mount перечитывает всё (D9).** См. «Переподключение».

## Как это соотносится с Django-версией

| Django (было) | Elixir (стало) |
|---|---|
| `showme*.html` — рендер монитора в файлы в каталоге шаблонов + `file.count` | `%MonitorState{mode, data}` в памяти процесса `MonitorBoard`; ноль записей на диск, работает на read-only каталоге |
| SSE-стрим снапшотов с ручным retry (и багом 100 мс-шторма) | Phoenix.PubSub `{:monitor_updated, state}` + LiveView с автопереподключением и backoff из коробки |
| Экраны судей опрашивают сервер по таймеру (`setInterval` + reversed URL) | Push: подписка на `"competition"`, событие `{:performance_started, id}` будит экран мгновенно; поллинга нет вообще |
| «Кто из судей на связи» — узнать нельзя (звонить по рации) | `UshuWeb.Presence`, тема `"presence:judges"`: панель секретаря с судьями по категориям, уход виден автоматически |
| Снапшот монитора — глобальный dict в памяти одного воркера (а до стабилизации — файлы) | Именованный супервизируемый процесс: сериализованный доступ, авторестарт, честная сходимость проекторов после краша |
| Сигналы Django (`post_save`) — синхронные хуки в том же запросе | PubSub-события — асинхронные сообщения между независимыми процессами, после коммита |
| Обрыв соединения → судья жмёт F5 и надеется | Автопереподключение клиента + полный re-derive состояния в `mount/3` |

Требования из `stabilize-django/specs/monitor-realtime/spec.md` переезжают так:
«снапшот в памяти процесса, без файлов» и «нет torn reads» — выполняются самой
конструкцией GenServer + одно-сообщение-один-снапшот; «reconnect с floor 2s» —
встроенным backoff LiveView; «рендер либо целиком, либо ничего» — правилом
«данные строит вызывающий ДО `publish_*`; упал при сборке — доска не тронута».
