# 02 — Ядро подсчёта очков: `Ushu.Scoring`

**Слой 2 из 7** в переписывании ushu на Elixir/Phoenix.
Зависит от: `elixir-01-foundation` (каркас проекта, mix, ExUnit).
От него зависят: `elixir-04-contexts` (загружает оценки из БД и вызывает это
ядро), `elixir-06-liveview-ui` (рендерит результаты).

## Что это за слой и зачем он первый после каркаса

Правила подсчёта — A (технические ошибки), B (качество), C (сложность),
бонус, тай-брейк за медали — это самая ценная и самая хрупкая логика ushu.
В Django-версии она размазана между `tablo/models.py` (методы
`calculateA/B/C`, `get_b_score`, `get_scores` на модели `Participation`) и
`tablo/views.py` (функции `counts`, `cmp`, `sort`) и переплетена с ORM:
чтобы посчитать оценку, нужно поднять цепочку
`Score → cclass → CombinationStatus → statuses → ElementStatus → element`.

В Elixir-версии мы делаем наоборот: **сначала** пишем чистый модуль
`Ushu.Scoring`, который не знает ни про базу, ни про процессы, ни про веб —
только функции над обычными структурами. Числа фиксируем «золотыми» тестами,
перенесёнными один в один из `tablo/test_scoring_golden.py`,
`tablo/test_scoring_rules.py` и `tablo/tests.py`. Все последующие слои
(Ecto-схемы, контексты, LiveView) будут строиться поверх уже доказанно
правильного ядра.

Если проводить параллель с тем, что ты знаешь из Kotlin: это **domain layer**
из Clean Architecture — чистые классы без аннотаций Spring и без JPA,
которые можно тестировать без поднятия контекста. Только в Elixir этот стиль
не «архитектурное решение поверх ООП», а естественный способ писать код.

## Ключевые концепции Elixir в этом слое

### 1. Иммутабельность: данных «на месте» не меняют вообще

В Elixir **все** значения неизменяемы. Не как в Kotlin, где `val` — это
неизменяемая *ссылка*, а объект за ней может мутировать (`val list =
mutableListOf(...)`), — а по-настоящему: нет ни одного способа изменить
существующий список, map или структуру. Любая «модификация» возвращает новое
значение:

```elixir
list = [1, 2, 3]
new_list = List.delete(list, 2)   # [1, 3]
list                              # по-прежнему [1, 2, 3]
```

Почему это важно именно здесь. В Django-версии функция согласования ошибок
судей A написана с мутацией:

```python
# tablo/models.py — Python, мутация second/third НА МЕСТЕ
for error in first:
    in_second = error in second
    if in_second:
        second.remove(error)      # <-- судья 2 «потратил» свою копию ошибки
    ...
```

Этот `remove` — не случайность, а **несущая часть правила**: совпавшие
ошибки «потребляются», чтобы одинаковые ошибки спаривались один к одному.
В Elixir мы выражаем то же самое рекурсией, где «изменённый» список — это
просто следующий аргумент:

```elixir
# идея: проходим ошибки судьи 1, "вычёркивая" совпадения из судей 2 и 3
defp consume([], _second, _third, agreed), do: ...
defp consume([err | rest], second, third, agreed) do
  {hit2, second} = take_by_code(second, err.code_id)
  {hit3, third}  = take_by_code(third, err.code_id)
  agreed = if hit2 or hit3, do: [err | agreed], else: agreed
  consume(rest, second, third, agreed)
end
```

Обрати внимание: `second = ...` внутри — это не мутация, а **rebinding**
(перепривязка имени к новому значению), как если бы в Kotlin ты писал
`var second = ...; second = second - err`. Старый список никуда не делся,
просто имя теперь указывает на новый.

Практическое следствие для судейской системы: никакая функция подсчёта не
может случайно испортить входные данные, и один и тот же вход всегда даёт
один и тот же выход. Гонки данных внутри чистого кода невозможны в принципе.

### 2. Pattern matching и guards: `if`-ов почти нет

Оператор `=` в Elixir — это не присваивание, а **сопоставление с образцом**
(match). Слева может стоять шаблон:

```elixir
{agreed, score_c} = Scoring.aggregate_a(errors, :y12_14)
[first | rest] = [1, 2, 3]        # first = 1, rest = [2, 3]
%{verdict: v} = mark              # вытащить поле из структуры/map
```

Самое мощное применение — **несколько тел одной функции**, выбираемых по
форме аргументов. То, что в Kotlin было бы `when`-каскадом или иерархией
классов, в Elixir — просто набор клауз:

```elixir
# возраст -> максимум судьи A, в центисотых (см. ниже про центибаллы)
def a_max(:adult), do: 500
def a_max(bucket) when bucket in [:y7_8, :y9_10, :y11, :y12_14, :y15_17],
  do: 700
```

`when ...` — это **guard**, дополнительное условие на клаузу. Заметь, что
второй клаузе перечислен весь допустимый enum: если кто-то передаст опечатку
`:adlut`, функция не «тихо посчитает как юниора» (как Django-шный
`age == AGE_18_plus` посчитал бы любой неизвестный int), а упадёт с
`FunctionClauseError` — прямо на тесте. Это философия «let it crash»:
невалидное состояние должно падать громко и рано, а не портить протокол
соревнований молча.

Ещё пример из ядра — решение по элементу судей C:

```elixir
defp decide(marks) do
  performed = Enum.filter(marks, &(&1.verdict == :performed))
  failed    = Enum.filter(marks, &(&1.verdict == :failed))

  cond do
    length(performed) >= 2 -> {:performed, hd(performed)}
    length(failed) >= 2    -> {:failed, hd(failed)}
    true                   -> :excluded    # нет большинства — исключаем
  end
end
```

`&(&1.verdict == :performed)` — сокращённая запись лямбды, аналог
Kotlin-овского `{ it.verdict == Verdict.PERFORMED }`. Ключевое свойство
правила: `:pending` (судья не отметил) не попадает **ни в один** из двух
фильтров — воздержание не может стать ни «выполнено», ни «провалено». В
Django это держалось на магическом `done == 2`; здесь — на именованном атоме
и структуре самой функции.

### 3. Атомы: enum без церемоний

`:pending`, `:performed`, `:failed`, `:adult` — это **атомы**: константы,
чьё значение — их собственное имя. Аналог Kotlin `enum class`, но без
объявления. Мы используем их для всех доменных перечислений:

```elixir
@type verdict :: :pending | :performed | :failed
@type age_bucket :: :y7_8 | :y9_10 | :y11 | :y12_14 | :y15_17 | :adult
```

`@type` — это typespec: документация типов, которую проверяет статический
анализатор (dialyzer) и показывает hexdocs. Не compile-time система типов,
как в Kotlin, но в связке с guards и тестами покрывает ту же потребность.
Django-версия кодировала те же понятия «сырыми» интами (`done ∈ {2,1,0}`,
возраст `4,0,5,1,2,3`) — при переносе в Elixir мы навсегда избавляемся от
магических чисел.

### 4. Структуры vs map: типизированные данные вместо ORM-объектов

**Map** — базовый словарь: `%{"key" => 1}` или `%{key: 1}`. **Struct** — это
map с объявленным именем и фиксированным набором ключей:

```elixir
defmodule Ushu.Scoring.Mark do
  @enforce_keys [:element_id, :position, :verdict, :score_c, :landing]
  defstruct [:element_id, :position, :verdict, :score_c, :landing]

  @type t :: %__MODULE__{
          element_id: pos_integer,
          position: non_neg_integer,
          verdict: :pending | :performed | :failed,
          score_c: non_neg_integer,   # 0.50 балла -> 50
          landing: boolean            # prizemlenie в Django
        }
end
```

Использование:

```elixir
mark = %Mark{element_id: 7, position: 0, verdict: :performed,
             score_c: 50, landing: false}
%Mark{verdict: v} = mark        # pattern matching по структуре
%{mark | verdict: :failed}      # "изменение" = новая копия с новым полем
```

Сравнение с знакомым тебе:

| | Kotlin | Elixir |
|---|---|---|
| Тип-носитель данных | `data class Mark(...)` | `defstruct` + `@type t` |
| «Изменение» | `mark.copy(verdict = FAILED)` | `%{mark | verdict: :failed}` |
| Обязательные поля | параметры конструктора | `@enforce_keys` |
| Опечатка в поле | ошибка компиляции | `KeyError` при компиляции структуры |

Ошибиться в ключе структуры (`%Mark{verdikt: ...}`) — ошибка **компиляции**,
в отличие от простого map. Именно поэтому входы ядра — структуры `Deduction`,
`BScore`, `Mark`, а не сырые map: это наш «типизированный порт» на границе
слоя. Слой `elixir-04-contexts` будет читать строки из SQLite через Ecto и
конвертировать их в эти структуры — ядро о Ecto не знает вообще.

### 5. Оператор pipe `|>`: конвейер вместо вложенных вызовов

`x |> f(a)` — это просто `f(x, a)`: результат слева подставляется первым
аргументом справа. Kotlin-аналог — цепочки `let`/extension-функций, но в
Elixir это основной стиль. Подсчёт тай-брейк-счётчиков:

```elixir
def tiebreak_counts(agreed_marks) do
  performed_moves =
    agreed_marks
    |> Enum.filter(&(&1.verdict == :performed))
    |> Enum.reject(& &1.landing)

  {
    Enum.count(performed_moves, &(&1.score_c > 30)),  # e4: > 0.30
    Enum.count(performed_moves, &(&1.score_c > 20)),  # e3: > 0.20
    Enum.count(performed_moves, &(&1.score_c > 10))   # e2: > 0.10
  }
end
```

Читается сверху вниз как предложение: «взять согласованные отметки →
оставить выполненные → выбросить приземления → посчитать по трём порогам».
Сравни с Django-версией на вложенных `filter(lambda ...)` в
`tablo/views.py::counts` — то же правило, но читать приходится изнутри
наружу.

Модуль `Enum` — твой главный инструмент, аналог Kotlin-овских
`filter/map/fold` на коллекциях: `Enum.filter/2`, `Enum.map/2`,
`Enum.reduce/3`, `Enum.frequencies/1`, `Enum.zip/1`.

### 6. Doctests: примеры в документации, которые запускаются как тесты

В `@doc` можно писать примеры сессии iex, и ExUnit **выполнит их** и сверит
вывод. Документация не может устареть — устаревший пример роняет тест:

```elixir
@doc """
Агрегат B-судей: повторившееся значение побеждает, иначе усечённое среднее.

## Examples

    iex> Ushu.Scoring.aggregate_b([950, 960, 960, 970])
    960

    iex> Ushu.Scoring.aggregate_b([940, 950, 960, 970])
    955

    iex> Ushu.Scoring.aggregate_b([nil, 0, 0])
    0
"""
def aggregate_b(values) do
  ...
end
```

И в тестовом файле одна строка:

```elixir
defmodule Ushu.ScoringTest do
  use ExUnit.Case, async: true
  doctest Ushu.Scoring   # <-- запускает все примеры из @doc
end
```

В Spring-мире ближайший аналог — если бы примеры из Javadoc автоматически
становились JUnit-тестами. Для тебя как изучающего это двойная выгода: сама
документация модуля `Ushu.Scoring` — это учебник по правилам судейства с
живыми числами.

### 7. ExUnit: тесты без поднятия «контекста»

```elixir
defmodule Ushu.Scoring.AggregateBTest do
  use ExUnit.Case, async: true

  # золотой случай из tablo/test_scoring_rules.py::test_repeated_value_wins
  test "повторившееся значение побеждает" do
    assert Ushu.Scoring.aggregate_b([950, 950, 970, 980]) == 950
  end

  test "при равной частоте берём большее" do
    assert Ushu.Scoring.aggregate_b([950, 950, 980, 980]) == 980
  end
end
```

`async: true` — тесты файла бегут параллельно с другими файлами: чистым
функциям нечего делить. Django-версии для тех же проверок нужен был
`django.test.TestCase` с транзакцией на каждую проверку, даже для чистых
методов (там честно писали `Participation()` без сохранения — но сам факт,
что чистые правила живут на ORM-модели, вынуждал тащить весь Django).
Здесь: `mix test` — и сотни проверок за доли секунды, без базы вообще.

Запуск: `mix test`, один файл — `mix test test/ushu/scoring/aggregate_b_test.exs`,
одна строка — `mix test path:42`.

### 8. Почему чистое функциональное ядро (и при чём тут гексагональная архитектура)

Из Kotlin ты знаешь Clean/Hexagonal Architecture: в центре — domain без
зависимостей, вокруг — адаптеры (JPA, web). В Spring это требует дисциплины:
ничто не мешает заинжектить репозиторий в доменный сервис.

В Elixir тот же принцип называется **functional core, imperative shell**:

```
┌────────────────────────────────────────────┐
│  shell: elixir-04 контексты (Ecto, Repo)   │   <- side effects, БД
│   ┌────────────────────────────────────┐   │
│   │  core: Ushu.Scoring                │   │   <- чистые функции
│   │  структуры in -> Result out        │   │
│   └────────────────────────────────────┘   │
│  shell: elixir-05/06 (PubSub, LiveView)    │   <- side effects, веб
└────────────────────────────────────────────┘
```

Оболочка (контексты) делает I/O: читает оценки из SQLite, маппит их в
структуры, вызывает ядро, сохраняет `final_c`, шлёт PubSub-событие. Ядро
принимает значения и возвращает значения. Выгоды конкретно для ushu:

- **Тестируемость чисел.** Все золотые случаи проверяются мгновенно и
  детерминированно. В Django часть тех же правил можно было проверить только
  через 8 SQL-запросов (`GetScoresQueryCountTest` это буквально фиксирует).
- **Безопасность пересчёта.** Пересчитать табло — значит заново вызвать
  чистую функцию; никакого скрытого состояния (Django кэшировал
  `_scores_cache` на инстансе, и это отдельно тестировалось).
- **Читаемость правил.** Правило целиком видно в одной функции, а не
  собирается из модели, менеджера и view-хелперов.

Отличие от Kotlin-версии этой идеи: здесь её не надо «защищать» — в модуле
без `Repo` в импортах эффект просто негде спрятать.

## Решения и почему (по design.md)

**D1. Все величины — целые центибаллы.** 7.00 → `700`, 0.05 → `5`,
пул движений 1.4 → `140`. Django держал float-ы и был вынужден чинить
округление: агрегат B `9.58` хранился как `957.999…`, и `int()` срезал
центибалл — в `stabilize-django` это исправляли на `round()`. Мы убираем сам
класс ошибки: если единица хранения — целое число сотых, артефактам двоичной
арифметики неоткуда взяться. Это тот же приём, что «деньги в копейках, не в
рублях с float». Float появляется только при отображении: `final_c / 100`.
Альтернативы: библиотека `Decimal` (корректно, но тяжеловесно — все легальные
входы и так кратны 0.01) и float с epsilon-сравнениями (отвергнуто — именно
эту граблю Django уже собрал).

**D2. Входы — структуры, не Ecto-схемы и не map.** `Deduction` (ошибка:
`code_id` + `value_c`), `BScore` (`base_c` + список `Deduction`), `Mark`
(вердикт + цена элемента + флаг приземления + позиция). Ядро остаётся
компилируемым и тестируемым без базы; Ecto-строки в структуры маппит слой
elixir-04. Равенство ошибок при согласовании — по `code_id`: в Django
сравнивались ORM-объекты (по pk), у нас структурное равенство было бы
слишком широким, поэтому ключ явный.

**D3. Согласование судей A — дословный перенос «потребляющего»
алгоритма.** Идём по ошибкам судьи 1, совпадения «вычёркиваем» из списков
судей 2 и 3, затем остатки судьи 2 сверяем с судьёй 3. Красивее было бы
посчитать частоты кодов (`Enum.frequencies`), но это **не эквивалентно**,
когда один судья ставит один код дважды: потребление спаривает копии один к
одному. Паритет с зафиксированным поведением важнее элегантности; на этот
краевой случай добавлен отдельный тест.

**D4. Судьи C: марки склеиваются по позиции (`position`), как Django-шный
`zip`.** Позиционный порядок sortedm2m в Django был несущим — у нас он
становится явной колонкой `position` (слой elixir-03), а ядро требует списки
одинаковой длины и падает при рассинхроне (вместо тихого обрезания хвоста,
которое сделал бы `Enum.zip`). Решение по элементу: ≥2 реальных
`:performed` → выполнено; иначе ≥2 реальных `:failed` → провалено и вычет из
пула (движения 140 / приземления 60, каждый не ниже 0, сумма не выше 200);
иначе — исключён («презумпция выполненности» без зачёта в тай-брейк).

**D5. Эффективная оценка B-судьи — отдельная функция
`BScore.effective/1`.** `nil` — только когда судья не ввёл ничего; честный
`0.00` — полноценный голос; вычеты не уводят ниже нуля. Агрегат
`aggregate_b/1` работает уже со списком `integer | nil`: повторившееся
значение побеждает (при равной частоте — большее), иначе усечённое среднее
`(sum − max − min) / (n − 2)` с округлением до центибалла; n=2 — среднее,
n=1 — само значение, пусто — 0. Формула не зависит от размера панели — для
стандартных четырёх судей совпадает с исторической `(sum − max − min) / 2`.

**D6. Тай-брейк — две маленькие функции.** `tiebreak_counts/1` считает
`{e4, e3, e2}` только по **согласованно выполненным движенческим** элементам
(пороги цены > 30/20/10 центибаллов); воздержание не считается «выполнено»
автоматически — исключённые элементы вообще не попадают в согласованный
список. `compare/2` сравнивает пары `{final_c, counts}` и возвращает
`:gt | :eq | :lt` — готовый компаратор для `Enum.sort/2`. Ветка Django-шного
`cmp` для незавершённых участников (сортировка по жребию) уедет в
elixir-04 — ей нужно состояние участия, которого чистое ядро не знает.

**D7. `assemble/1` без мемоизации.** Django кэшировал `get_scores` на
инстансе, потому что сортировка звала его O(n log n) раз и каждый вызов
стоил 8 SQL-запросов. Чистая функция над структурами в памяти стоит
микросекунды — контексты просто соберут `Result` по разу перед сортировкой.
`Result.no_show/0` — канонический нулевой результат, заменяющий сентинель
`FINISHED && finalscore == 0`.

**D8. Возрастной максимум — тотальная функция над enum с guard-ом.**
Опечатка в атоме — громкий `FunctionClauseError`, а не тихий «юниорский»
максимум.

**D9. Тесты — прямой порт трёх Django-файлов + doctests.** Каждый золотой
случай ссылается комментарием на исходный Python-тест. Два
`assertAlmostEqual` (1.5 и 1.7) превращаются в точные `== 150` и `== 170` —
ещё один дивиденд целых центибаллов.

## Как это соотносится с Django-версией

| Django (было) | Elixir (становится) |
|---|---|
| `Participation.calculateA(judge_error_lists, age)` | `Ushu.Scoring.aggregate_a(deduction_lists, age_bucket)` |
| `Participation._errors_agreed_by_majority` (мутация `remove`) | приватная рекурсия с потреблением списков (иммутабельно) |
| `MAX_A_SCORE = 7.0` / `MAX_A_SCORE_ADULT = 5.0` | `a_max/1`: `:adult -> 500`, иначе `700` (центибаллы) |
| `Score.get_b_score()` (nil / кламп в 0 / round 2dp) | `Ushu.Scoring.BScore.effective/1` (nil / `max(0, …)`, целые) |
| `Participation.calculateB(raw_scores)` c `Counter` | `aggregate_b/1` c `Enum.frequencies/1` |
| `round(calculateB(...) * 100)` — фикс усечения | не нужен: агрегат уже целый; округляется только деление усечённого среднего |
| `Participation.calculateC(judge_status_lists)` | `aggregate_c(marks_per_judge)` |
| `ElementStatus.done ∈ {2, 1, 0}` | `Mark.verdict ∈ {:pending, :performed, :failed}` |
| `element.prizemlenie` | `Mark.landing :: boolean` |
| порядок sortedm2m (`CombinationStatus.statuses`) | явное поле `Mark.position` (колонка в elixir-03) |
| `Participation.get_scores()` + `_scores_cache` | `assemble/1 -> %Result{}`, без мемоизации |
| `items['final_b'] + 5` при бонусе | `+5` центибаллов к вкладу B в `assemble/1` |
| сентинель `PS_FINISHED && finalscore == 0` (неявка) | состояние `:no_show` → `Result.no_show/0` |
| `views.counts(valids)` → `(e4, e3, e2)` | `tiebreak_counts(agreed) -> {e4, e3, e2}` |
| `views.cmp` + `functools.cmp_to_key` + `views.sort` | `compare/2 -> :gt/:eq/:lt` (+ сортировка по жребию — в elixir-04) |
| `tablo/tests.py`, `test_scoring_rules.py`, `test_scoring_golden.py` | `test/ushu/scoring/*_test.exs` + doctests, те же числа |

Контрольные числа, которые обязаны сойтись (все — из Django-тестов):

- A: нет согласия → 7.00; трое согласны (1.5) → 5.50; двое из трёх (2.0) →
  5.00; согласие только судей 2 и 3 (1.0) → 6.00; взрослые без согласия → 5.00.
- B: `[9.5, 9.5, 9.7, 9.8] → 9.5`; `[9.5, 9.5, 9.8, 9.8] → 9.8`;
  `[9.4, 9.5, 9.6, 9.7] → 9.55`; `[7.0, 9.0, 8.0] → 8.0`; `[9.4, 9.6] → 9.5`;
  `[9.3] → 9.3`; `[nil, 0.0, 0.0] → 0.0`; `[nil, nil] → 0`.
- C: все выполнили → 2.0; все провалили движение 0.5 → 1.5; все провалили
  приземление 0.3 → 1.7; `(pending, performed, performed)` → 2.0;
  `(pending, failed, failed)` → 1.5; `(pending, performed, failed)` и
  `(pending, pending, performed)` → исключено, 2.0.
- Финал: 600 + 960 + 200 = 1760 → 17.6; с бонусом 1765 → 17.65;
  B `[9.57, 9.59, 9.4, 9.7]` → вклад ровно 958 → финал 17.58.
- Тай-брейк: выполненное движение 0.5 → `{1,1,1}`; `:pending`/`:failed`/
  приземление → `{0,0,0}`; при равных финалах побеждает `{1,1,1}`.
